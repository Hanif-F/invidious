# Foundation and shell

The foundation agent owns the shared viewport rule, page shell, navigation, general-purpose menus and dialogs, and notice geometry. Land the shared changes first. Feature agents use this contract for local layouts and overlays. [Work order](README.md#agent-work-order)

## F1. Layout and accessibility

- Use the CSS media condition `(width < 768px), (width < 960px) and (orientation: landscape) and (height <= 500px)` for the phone shell and phone-specific page rules. Mirror it in a single shared `matchMedia` query wherever behavior must know whether the phone shell is active. Keep layout keyed to the viewport and player gestures keyed to pointer capability. A mouse at 390 px receives the phone layout with keyboard and pointer access. A coarse pointer at 1280 px keeps the existing touch player and wider page layout.
- Apply the phone media condition to shared shell gutters and local reflows. Use 12 px as the phone page gutter. Use logical padding and margins, `min-inline-size: 0` on shrinking children, and tracks such as `minmax(0, 1fr)`. Preserve aspect ratios and constrain media to its container. Wrap long tokens and translated labels at the component that owns them. Keep intentional truncation on dense metadata only where the important action or title remains discoverable. Fix the source of document overflow instead of clipping the page.
- Size prominent buttons, icon controls, interactive menu rows, and checkbox or radio labels toward a 44 × 44 CSS px hit area. Keep gaps between neighboring actions. Increase label hit areas around native controls and preserve the text and tab order. Vendor media controls may use their existing geometry when a blanket target change would crowd the control bar. Verify their hit areas and accessible labels independently.
- Keep pinch zoom and browser text enlargement. Use logical positioning for RTL and retain direction-specific icons and media timeline semantics. Keep visible focus indicators in all themes and forced colors, including inside scrollers. Ensure sticky chrome and notices leave focused controls and anchor destinations visible. Avoid adding animation to simple reflows. Respect reduced motion when transitions already exist.
- Account for safe-area insets wherever chrome, a drawer, or an overlay meets a viewport edge. Use dynamic viewport bounds with a fallback. For keyboard-sensitive overlays, use the visual viewport where the browser exposes it and verify the fallback with a reduced available height. Centralize the shared geometry so each dialog does not install its own global resize handlers.

**Accept when** every phone page can reflow without document-wide horizontal scrolling. Horizontal scrolling belongs to purpose-built scrollers such as channel tabs, media carousels, and read-only tables. Verify 320 px, short landscape, RTL, enlarged text, forced colors, and an equal-width mouse viewport. Wider shell padding and control styling retain their current geometry.

## F2. Header, search, and navigation

1. Reflow the shared header into a top row and the existing search form underneath. Keep the drawer trigger and wordmark at logical start and theme/account controls at logical end. Keep a single global search form and its original submit behavior, value, focus shortcut, and private GET/POST selection. Search home uses its main form. Point the search keyboard shortcut at the available search field.
2. Keep the top row sticky in portrait. Keep search in page flow below it. In landscape phone mode, keep both rows in flow. Derive drawer and anchor offsets from the actual top row rather than a desktop-only constant. Keep branding, sign-in/account, Settings, theme, and sign-out available with the same role and config rules. Allow long account names and menu labels to wrap in the menu.
3. Render one sidebar navigation landmark using the existing link list. Give it a native disclosure presentation in phone mode before enhancement, including when the navigation script fails to load. Place that fallback immediately after the header search and before main content. The disclosure is closed by default on a phone and available by keyboard and touch. Keep the ordinary sidebar links visible at wider widths. If a shared `details` wrapper is used, ensure its default state and the wider CSS keep links reachable with scripts disabled.
4. Extend the existing Watch drawer controller to phone mode. Start with the drawer closed, show full link labels while open, and keep closed links out of the tab order. In enhanced mode position the same sidebar over the page with a scrim. Move focus to the first usable link. Keep keyboard focus within the drawer and its trigger, make the background inert, prevent background scroll, and preserve the prior scroll position. Close on the trigger, outside tap, Escape, or link activation. Restore focus to the trigger after dismissal. When navigation is proceeding, let the destination take focus.
5. Use transient phone drawer state. When crossing into phone mode, close the drawer and clear wider modal or collapsed presentation. When leaving phone mode, clear the scrim, inert state, and scroll lock before applying the stored desktop collapse state or the existing Watch rail. Keep storage profile changes, cached page restores, and reinitialization from leaving a hidden focused node or duplicate event handlers.

**Accept when** guest and signed-in people can reach every configured destination from 320 px, the trigger and scrim behave consistently in both directions, and resizing with the drawer open restores the correct shell and focus. Verify hidden controls cannot be tabbed to, top-row/search scrolling matches portrait and landscape, and the unenhanced phone disclosure opens with ordinary links and forms. Verify the desktop rail, Watch drawer, sidebar preference, native account menu, and one navigation landmark.

## F3. Menus, dialogs, and feedback

- Keep the existing `details` menus and `dialog` elements. Reuse menu initialization on `iv:content-added`. For open menus, account for anchor position, logical direction, scroll, rotation, and the visible viewport. Maintain an 8 px gap from usable viewport edges where space permits. Give long menus their own vertical scroll. Close or reposition when the anchor moves out of view. Native details links and forms remain reachable when JavaScript is unavailable, including More outside the channel tab scroller.
- Size centered dialogs within the usable inline and block space. Keep the title and close affordance visible and allow the content and form actions to scroll into reach. Prefer one scrolling body. Keep submit and cancel in the normal tab order, and scroll a focused field or validation error above a simulated keyboard. Let actions wrap or stack. Preserve desktop geometry and existing fullscreen-specific player overlay bounds.
- Open one modal at a time. Route dismissal through the existing owner so form state, dismissal rules, and focus restoration remain consistent. When the opener was inside a closed menu, use that menu's visible summary as the return target. When a row disappears after a confirmed action, use the nearest surviving related row or section heading. Ensure modal close and viewport transitions release any scroll locks and inert state.
- Reflow common notices and profile recovery into a bounded-width surface with wrapping status and reachable dismiss, retry, or refresh. Keep notices out of the focused control's way in short viewports. Preserve existing status/alert announcements and explicit recovery actions.

**Accept when** account and row menus, navigation overlays, Save to playlist, Download, DeArrow, chat settings, shortcut help, batch confirmation, notices, and profile recovery fit or scroll within usable bounds at 320 px and short landscape. Test edge-anchored menus, long text, keyboard focus, scroll, rotation, and appended menu nodes. Check that opening and closing an overlay preserves the underlying draft, form, or player state.
